#질문
높이맵 이미지 설명


#답장
높이맵(heightmap)은 지형의 높이를 그레이스케일 이미지 한 장으로 저장한 것입니다. 픽셀의 밝기가 곧 그 위치의 고도예요. 검정=최저, 흰색=최고.

2번 펄린 노이즈가 "높이를 실행 중에 계산"했다면, 3번 높이맵은 "높이를 미리 그려둔 걸 읽어온다"는 차이입니다. Evaluate(x, z) 자리에 SampleImage(x, z)만 갈아끼우는 구조라는 건 이미 문서에 적어두신 대로고요.

비트 심도가 제일 중요합니다
심도	높이 단계	결과
8비트	256	진폭 30이면 계단 하나가 0.12 — 계단 현상(terracing)이 눈에 보임
16비트	65,536	진폭 30에서 계단 하나가 0.00046 — 사실상 연속

8비트가 특히 나쁜 이유는 법선 때문입니다. 높이는 0.12 차이라 대충 넘어가도, 이웃 높이의 중앙 차분으로 법선을 뽑으면 계단면은 완전한 평면 → 계단 옆면은 수직 → 솔리드 셰이딩에서 등고선 무늬가 선명하게 드러납니다. GridMesh::Generate가 중앙 차분을 쓰고 있으니 그대로 겪게 될 문제예요.

JPG는 절대 쓰면 안 됩니다. DCT 손실 압축이라 8×8 블록 경계마다 미세한 높이 점프가 생기고, 그게 전부 법선에 증폭돼서 격자 무늬로 나옵니다. 눈으로 보면 멀쩡한 이미지가 지형으로 만들면 지저분해집니다.

권장: 16비트 그레이스케일 PNG 또는 RAW(R16). RAW는 헤더가 없어서 fread 한 방이면 되고 (World Machine, Gaea, Unity가 다 쓰는 포맷), PNG는 lodepng 같은 단일 파일 라이브러리를 하나 넣으면 됩니다.

좌표 매핑
월드 (x, z) → UV [0,1] → 픽셀 (u * (W-1), v * (H-1))

두 가지를 결정해야 합니다.

V축 방향. 이미지는 위에서 아래로 행이 증가하고, 월드 Z는 보통 앞으로 증가합니다. 뒤집을지 말지 한 번 정해두지 않으면 나중에 "지형이 위성사진과 남북이 반대"인 상황이 옵니다.

경계 처리. Clamp(가장자리 늘리기) / Wrap(타일링) / Mirror. 그리드가 이미지보다 크면 뭐가 나올지 결정하는 부분입니다. 10번 무한 청크를 염두에 두면 Wrap이 유용하지만, 그러려면 이미지 자체가 seamless여야 합니다.

샘플링 방식

최근접(nearest): 픽셀 하나가 그대로 평평한 사각형. 텍셀 경계마다 수직 벽. 이미지 해상도 = 그리드 분할 수일 때만 쓸 만합니다.

바이리니어: 실무 기본값. 다만 C⁰ 연속이라 텍셀 경계에서 기울기가 꺾입니다. 펄린에서 fade 함수를 6t⁵-15t⁴+10t³로 쓴 이유와 정확히 같은 문제인데, 여기선 fade를 마음대로 못 넣습니다(넣으면 높이가 왜곡됨). 분할 수가 텍셀 밀도보다 훨씬 촘촘하면 이 꺾임이 보이기 시작해요.

바이큐빅 / Catmull-Rom: C¹ 연속이라 법선이 부드럽습니다. 16개 텍셀을 읽으니 비용은 4배. 저해상도 이미지를 크게 늘려 쓸 때 값어치를 합니다.

해상도와 분할 수의 관계

이상적인 건 1텍셀 = 1정점입니다. 512×512 이미지에 512분할 그리드면 보간 자체가 필요 없어요.

그리드가 더 촘촘하면 → 없는 디테일을 만들어내는 게 아니라 보간만 늘어남 (정점 낭비). 펄린 노이즈를 detail layer로 더해주는 게 정석 조합입니다.
그리드가 더 성기면 → 이미지 디테일이 정점 사이에서 잘려나갑니다. 2번 문서의 "가장 잘은 굴곡 < 셀 크기 × 2" 규칙이 그대로 적용돼요. 미리 다운샘플링(박스 필터 평균)해서 앨리어싱을 줄이고 써야 합니다.
최종 높이 공식
cpp
float h = (Sample(u, v) / maxValue) * heightScale + heightOffset;

maxValue는 255 또는 65535. 실제 지형 데이터를 쓸 거면 여기가 미터 단위와 연결되는 지점입니다 — 예를 들어 SRTM 데이터에서 고도 0~4000m 구간을 뽑았다면 heightScale = 4000 / 월드단위비율이 되죠. HUD에 실제 높이 범위를 띄우는 건 2번에서 만들어두셨으니 그대로 재사용하면 됩니다.

데이터를 어디서 구하나
직접 그리기 — Photoshop/GIMP에서 16비트 그레이스케일로. 학습용으로는 원, 사각형, 그라디언트 같은 도형으로 먼저 검증하는 게 좋습니다 (원 하나 그려서 정확히 원뿔/원기둥이 나오는지 확인).
실제 지형 — USGS EarthExplorer, SRTM(전 지구 30m), 국토지리정보원 수치표고모델.
절차적 툴 — World Machine, Gaea, Blender. 침식 시뮬레이션이 들어간 진짜 같은 지형이 나옵니다.
2번 결과를 저장 — 이미 검증 단계에서 512×512 이미지로 뽑아보셨죠. 그 코드를 export 기능으로 만들면 "펄린으로 만들고 → 이미지로 저장 → 3번에서 로드"가 되어 두 기법이 이어집니다. 3번의 검증 수단으로도 훌륭하고요 (같은 파라미터의 2번과 3번이 같은 지형이면 로더가 맞는 것).
CPU 샘플링 vs GPU

지금 구조는 CPU에서 높이를 계산해 정점에 굽는 방식이라 3번도 CPU 샘플링이 자연스럽습니다. 다만 높이맵의 진짜 장점은 GPU에서 바로 쓸 수 있다는 것이에요 — 정점 셰이더에서 SampleLevel로 텍스처를 읽어 정점을 밀어 올리면(vertex displacement) CPU 재생성이 아예 없어집니다. 7번 하드웨어 테셀레이션에서 도메인 셰이더가 높이맵을 직접 읽는 게 바로 그 그림이고, 3번에서 이미지를 Texture2D로도 올려두면 그때 재활용됩니다.
